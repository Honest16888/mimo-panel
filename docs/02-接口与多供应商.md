# 02 · 接口与多供应商

## MiMo 平台（三个接口都有）

| 接口 | 地址 | 说明 |
|---|---|---|
| 余额 | `GET /v1/platform/balance` | `balance_infos[]`，含总可用、现金、赠金、冻结、授信 |
| 日用量 | `GET /v1/platform/usage/daily?start_date=&end_date=` | UTC 自然日，跨度 ≤ 31 天，最早 2026-09-01 |
| 日账单 | `GET /v1/platform/billing/daily?start_date=&end_date=` | 原价、折扣、赠金、实付 |

鉴权：`Authorization: Bearer sk-xxxx`，同时带 `api-key` 头更稳。
注意 **Token Plan 的 `tp-` Key 不能用于账务接口**。

用量接口返回扁平行，关键字段：

```json
{
  "date": "2026-11-19", "resource_type": "model",
  "name": "mimo-v2.6-pro", "masked_api_key": "sk-****3f2a",
  "consumed_amount": "3.912000",
  "input_cache_hit_amount": "0.15", "input_cache_miss_amount": "2.10", "output_amount": "1.66",
  "total_tokens": 1234567,
  "input_cache_hit_tokens": ..., "input_cache_miss_tokens": ..., "output_tokens": ...,
  "request_count": 207, "inference_type": "online"
}
```

`resource_type=plugin` 的行是插件调用（如 web-search），单独灰柱。

## 其他厂商

| 厂商 | 地址 | 结构 | 用量接口 |
|---|---|---|---|
| DeepSeek | `GET https://api.deepseek.com/user/balance` | `balance_infos[].total_balance / granted_balance / topped_up_balance` | **无** |
| Kimi（Moonshot） | `GET https://api.moonshot.cn/v1/users/me/balance` | `data.available_balance / cash_balance / voucher_balance` | 无 |
| 硅基流动 | `GET https://api.siliconflow.cn/v1/user/info` | `data.totalBalance / chargeBalance / balance` | 无 |
| OpenRouter | `GET https://openrouter.ai/api/v1/credits` | `data.total_credits - data.total_usage`，USD | 无 |
| 自定义 | 用户填地址 + 字段路径（默认 `data.balance`） | 任意 JSON | 无 |

DeepSeek 的余额结构与 MiMo **完全同构**，所以共用解析器（`parse="mimo"`），只换 URL。
其余各家用一个 `normalizeBalance(body, parse, account)` 入口统一成内部结构：

```js
{
  currency, total_available, cash_balance, gift_balance, frozen_balance,
  credit_available
}
```

页面永远只认这七个字段，供应商差异到此为止。币种为 USD 时余额符号自动换成 `$`。

## 多账号模型

```js
state.accounts = [
  { name: "MiMo 主力", brand: "mimo",     key: "sk-...", url: "", path: "", currency: "CNY" },
  { name: "DeepSeek",  brand: "deepseek", key: "sk-...", url: "", path: "", currency: "CNY" }
];
state.accIdx = 0;          // 当前账号
```

- 切换账号 = 换 `accIdx` → 同步 `state.key` → 清空旧数据 → 立即刷新
- 设置里可以增删账号、改供应商、给自定义接口填 `url` 与点路径
- 只有当前账号是 MiMo 时才把 Key 写入原生后台（否则后台预警/小组件会用错号）

## 只有余额接口时怎么体现"用量"

官方只给余额的账户，我们不编造数据，而是**用余额快照反推消费**：

```
snapshots = { "DeepSeek|deepseek": { "2026-11-18": {bal: 98.2}, "2026-11-19": {bal: 86.4} } }
```

- 每次同步成功写一条当天快照（同一天覆盖更新）
- 相邻两天做差：`delta = 前一天余额 - 当天余额`
- `delta > 0` 视为消费，计入**后一天**；`delta ≤ 0` 视为充值/不变，当日记 0
- 推算结果生成与 MiMo 同构的用量行（`consumed_amount` = delta、`output_amount` = delta、`synth: true`），
  因此趋势图、明细、日账单、余额可撑天数这些模块**不需要任何额外分支**

代价与边界（界面上也写明了）：

- 精度取决于打开频率：一天只开一次，两天的消耗会合并到后一天
- 第一份快照没有参照，第一天为 0
- 充值当天记 0，充值后的消耗从次日开始统计
- 调用次数 / Token 无法推算，概览里直接显示"该厂商不支持"

## 缓存优化提示的算法

MiMo 返回了各类金额，所以能反推实际单价：

```
缓存命中单价 = input_cache_hit_amount / input_cache_hit_tokens
未命中单价   = input_cache_miss_amount / input_cache_miss_tokens
若全部命中，花费 = total_input_tokens × 命中单价
可省金额 = 未命中花费 - (未命中 token × 命中单价)
占比     = 可省金额 / 未命中花费      ← 分母用"未命中花费"，不是总花费
```

早期版本分母写成总花费，导致占比明显偏小，已修正。
